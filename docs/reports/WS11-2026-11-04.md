## À relire

- **Surplus** : le « surplus » affiché est le surplus *coté* (somme des `quotedOut` du plan moins `amountOut`), pas le remboursement on-chain réel (0,47 wARS pour la tx 0x7951… dans mon fixture, valeur lue dans les logs : transfert de 0,47 wARS au payeur). Il est libellé comme coté.
- Le tx 0x7951… des fixtures utilise `costBps 9 / savingsBps 21` inventés (les vraies valeurs de prod ne sont pas lisibles on-chain).
- Compteur « failed » : inclut aussi les reverts / échecs techniques, pas seulement les refus (voir Bloqué).
- Les clôtures quotidiennes sont datées par la date locale du marchand (clé du flag), les autres compteurs en UTC.
- Cache mémoire par instance Vercel (comme le limiteur existant).
- Chaque requête de `/proof` fait ~5 requêtes SQL supplémentaires (limites 50 / 14 jours).
- Adresse agent : `AGENT_ADDRESS` si défini, sinon constante `0x9E82…ccd5`.

## Bloqué

Données absentes pour des entrées complètes (non modifié, par consigne) :
- **Refus nominatifs** (price guard, caps, self-payment) : `SignerRefusedError` / `SolveResult.ok=false` ne sont écrits nulle part de façon structurée ; seul `submissions.error` (texte libre, non publié) existe pour les submissions échouées. Proposition : écrire un flag/une table `agent_events(kind, at, code)` côté web (`/api/invoices/*/quote`) et relayer.
- **Remboursement réel du surplus** : l'événement `Paid` n'a pas le montant remboursé et `payments` ne le stocke pas. Proposition : colonne `refunded_out` dans `payments`, remplie par l'indexer depuis les logs `Transfer` (token de sortie vers le payeur).
- **Reminders / closes par marchand ou horodatage précis** : seuls les comptes par jour sont exposés (volontaire).
- Les `reason` stockés dans les flags `gas_grant:*` (invoiceId, token) n'ont pas été utilisés pour ne pas lier un grant à un paiement.
