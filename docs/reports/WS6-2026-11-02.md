## Fait

### `packages/indexer`
- **`startIndexer(opts)`** (`src/indexer.ts`). Loop:
  `head = getBlockNumber(cacheTime 0)` → `safe = head - confirmations` → `getLogs(Paid)` on
  `[cursor, min(safe, cursor + range - 1)]` → block timestamps (one `getBlock` per block that has a log) → one DB
  transaction → outbox drain.
  - **Cursor:** `chain_cursor.router_paid` = **next block to scan**. It is created at `fromBlock` on first run,
    raised to `fromBlock` if the stored value is lower, and moved to `to + 1` in the **same transaction** as the batch.
    The transaction locks the cursor row (`SELECT … FOR UPDATE`) and aborts (`CursorMovedError`) if another writer
    moved it ahead. This protects against two indexers running at once.
  - **Range:** starts at `maxBlockRange` (2000). It halves, down to 1, on range-too-large errors or timeouts
    (`isRangeError`: about ten provider phrasings, code -32005, HTTP 413/504, viem `TimeoutError`; rate limits are
    excluded). It doubles back after 10 successful batches.
  - **Other errors:** exponential backoff from 1 s to 60 s. The cursor is re-read from the DB after every error.
  - **`stop()`:** wakes the sleep, lets the in-flight batch commit, then resolves. Tests check that no RPC call
    happens after `stop()`.
- **Reconciliation** (`src/reconcile.ts`, rule from §5). Per log, in the batch transaction:
  1. Dedupe on `(txHash, logIndex)` against `payments` and `unmatched_events`. Re-scanning a range is a no-op.
  2. Look up the invoice with `SELECT … FOR UPDATE`, so web or relayer can't change its status during the check.
  3. Outcomes:
     - Unknown id → `unknown_invoice`.
     - `merchant`, `tokenOut` or `amountOut` differs → `term_mismatch`; the payload lists each mismatch.
     - Terms match but the invoice already has a payment → `already_paid`. This is a double payment.
     - Terms match but the invoice is `expired` or `cancelled` → `paid_while_expired` / `paid_while_cancelled`.
     - These last three mean the merchant **really received the money**. Each one logs
       `indexer_alert_merchant_paid_unmatched` (level `alert`) and queues one `notifier.text` to the merchant (es/pt/en).
       `term_mismatch` and `unknown_invoice` only log a warning, so a griefer can't spam the merchant.
     - `open` or `submitted` → insert into `payments`. `paidAt` is the block timestamp. If the live submission's payer
       matches, `legs` come from it and `costBps` / `savingsBps` from its quote plan. Then
       `transitionInvoice(open|submitted → paid, {paidAt})`.
  4. Live submission (`pending`/`sending`/`sent`):
     - Same payer → `confirmed`, and `txHash` is set to the on-chain one (this covers a gas-bumped replacement).
     - Other payer → `failed` with "superseded".
- **Notification outbox** (`src/outbox.ts`, design choice):
  - Entries are rows in `flags`: `outbox:invoice_paid:<invoiceId>` and `outbox:alert:<txHash>:<logIndex>`.
  - They are written **in the reconciliation transaction**, only when a new payment or unmatched row is inserted, with
    `ON CONFLICT DO NOTHING`. A crash after commit therefore can't lose a notification, and reprocessing can't create
    a second one.
  - The outbox is drained after each batch and on every tick. Success deletes the entry. Failure sets `attempts++`,
    `lastError` and `nextAttemptAt` (backoff from 5 s, capped at 1 h). After 20 attempts the entry is marked `dead`
    and an alert is logged.
  - The cursor never waits for Telegram. Delivery is **at-least-once**: a crash between the notifier returning and
    the delete would resend.
- **`expireInvoices(db, now)`:** one `UPDATE … WHERE status='open' AND expires_at < now`. It never touches `submitted`
  and returns the count. `expires_at == now` stays open because the on-chain deadline is inclusive.
- **Tests:**
  - Setup: PGlite, plus **anvil spawned by the test** with `test/fixtures/PaidEmitter.sol`. That contract emits the
    exact `Paid` event; its bytecode is in `PaidEmitter.bin` and is rebuilt with `pnpm --filter @cobra/indexer fixture`.
    A custom viem transport records and sabotages RPC calls.
  - Covered:
    - open→paid and submitted→paid (legs, bps, submission confirmed);
    - superseded submission;
    - idempotent replay after rewinding the cursor;
    - restart from the cursor;
    - the three kinds of term mismatch, and unknown invoice;
    - expired, cancelled and double-paid → alert sent once;
    - confirmations lag;
    - range halving;
    - notifier failure doesn't block, then exactly one delivery;
    - generic RPC error → backoff → recovery;
    - clean stop;
    - concurrent-cursor guard;
    - rollback of the whole batch;
    - expiry;
    - `isRangeError` cases.

### `packages/db/src/queries` (new, export `@cobra/db/queries`)
- `listInvoicesByMerchant(db, merchantId, {status?, limit?, before?})`: newest first, keyset pagination.
- `countInvoicesByStatus`.
- `dailyTotalsByMerchant(db, merchantId, {from, to, timezone?})`: merchant-local day of `payments.paid_at`, grouped
  by (day, currency, tokenOut). Sums are exact `numeric` values returned as strings. `localDay(date, tz)` gives
  "today" for the daily close.
- `paymentCsvRows` + `toCsv`: RFC 4180 output, with a guard against formula injection (`=HYPERLINK…` is prefixed with `'`).

## À relire
- **Confirmations default = 5, not 2.** Celo is an OP-stack L2 with blocks of about 1 s, so 5 blocks is about 5 s of
  added latency at the counter. That is enough for sequencer-level reorgs of the unsafe head.
  - Residual risk: a reorg deeper than 5 blocks before L1 batch inclusion. It would take a sequencer failure or
    equivocation, an incident affecting all of Celo. In that case a `payments` row could point to a tx that no longer
    exists. That row is never auto-reverted.
  - Mitigation, not done: a periodic job re-checks `getTransactionReceipt` for payments younger than the L1
    finalization window. `safe`/`finalized` tags would cost minutes of latency, too slow for a point of sale.
  - Pass `confirmations: 2` if WS3 prefers the old value.
- The submission is set to `confirmed`/`failed` by the indexer without a status guard against the relayer. WS3 should
  make sure the relayer never moves a `confirmed` submission back.
- Invoice ids are looked up **in lowercase** (viem decodes bytes32 that way). WS5 must generate lowercase ids.
- The outbox lives in `flags` (`outbox:*` keys). It's practical, but it mixes operational flags with a queue; see the
  proposal below.
- Operator alerts are only `log(..., {level: "alert"})`. The worker (WS3) should route `level=alert` to
  `OPERATOR_TELEGRAM_CHAT_ID`.

## Interface changes (proposals, not applied)
1. `IndexerOptions.confirmations` comment: "default 2" became "default 5". This is a doc/default change only; the
   signature is unchanged.
2. `packages/db/package.json`: added the export `"./queries"`. This is additive.
3. Proposal: add `payments.notified_at timestamptz` (plus `unmatched_events.notified_at`). It would replace the flags
   outbox with `WHERE notified_at IS NULL`.
4. Proposal: a unique index on `unmatched_events(tx_hash, log_index)`. Today dedupe relies on select-then-insert under
   the cursor lock.
5. Open question: allow `expired → paid` in `INVOICE_TRANSITIONS` when the indexer sees a matching `Paid` event. The
   router enforces `block.timestamp <= deadline`, so a payment made just before the deadline but indexed after
   `expireInvoices` is legitimate. It is currently recorded as `paid_while_expired` and the merchant is alerted.
   Alternative: the worker calls `expireInvoices(db, new Date(Date.now() - 60_000))`, a grace period.
