# WS8 — test end-to-end sur fork anvil de Celo mainnet (2026-11-04)

## Fait

- Un test e2e qui rejoue la démo filmée à travers les packages, sur un fork anvil de Celo mainnet (chain id 42220, bloc = tête - 20, routeur déployé `0xfe38...e458` du fork).
- Commande : `pnpm test:e2e` (racine). Durée mesurée : environ 12 à 14 s (8 tests, le fork démarre en 2 à 3 s). Hors de `pnpm test` : fichiers `*.e2e.ts`, config `apps/worker/vitest.e2e.config.ts`.
- Skip propre (8 tests « skipped », avertissement) si `anvil` est absent ou si le RPC de fork est injoignable (vérifié avec `E2E_FORK_URL=http://127.0.0.1:1`). Variables optionnelles : `E2E_FORK_URL`, `E2E_FORK_BLOCK`.
- Scénarios (tous verts) :
  - scène 2 : onboarding AR via le bot, `cobrar 100 prueba`, payeur avec USD₮ et 0 CELO, quote Uniswap V3 réelle, une signature EIP-3009, soumission, relayer, `CobraRouter.pay`; assertions : le marchand reçoit exactement 100 wARS, le routeur ne garde rien, le surplus est remboursé (dépense <= amountIn), suffixe ERC-8021 `celo_502e1bea2794` à la fin de l'input, `submissions.status = confirmed`, ligne `payments`, `invoices.status = paid`, `/status` avec lien explorer, message Telegram « Pago recibido » avec le hash;
  - scène 3 : `cobrar 1000 café`, payeur avec wARS et 0 CELO; quote PERMIT2 avec `needsPermit2Approval`; le gas grant du relayer envoie exactement 0,05 CELO (tag ERC-8021, flag `gas_grant:`); approbation Permit2 par le payeur; re-quote; signature Permit2; payé; notification;
  - split à deux jambes USDC + USD₮ (EIP-3009 x2) vers wARS;
  - USD₮ vers wBRL pour un marchand BR (notification en portugais);
  - négatifs : signature sur montant/nonce modifié ou d'un tiers rejetée par l'API (`bad_signature`, aucune submission, rien de payé); signature valide rejouée contre une facture dont le marchand a été remplacé en base (insertion directe de la submission) : le relayer la marque `failed` (`leg0:signature_not_payer`), aucun mouvement de fonds.
- Documentation : `docs/testing-e2e.md`.

## À relire

- Constat important : sur le fork, toutes les clés publiques d'anvil ont du code EIP-7702 (délégation `0xef0100...` vers des contrats « sweeper »). Résultat : USD₮ vérifie la signature via ERC-1271 et revert `TetherToken: invalid signature`. Le harness remet `setCode(addr, 0x)` sur ces comptes, uniquement sur l'anvil local. Pas un bug produit, mais utile à savoir : un vrai payeur EOA délégué en 7702 passerait par ERC-1271 (la chaîne API/relayer est-elle prévue pour ça ? `verifyTypedData` de viem gère 1271, mais la signature EIP-3009 `(v,r,s)` encodée dans `pullData` n'est pas du 1271).
- Les taux de référence (garde de prix du solver, plafonds du relayer) sont dérivés des pools du fork, pas des API FX : le test valide la plomberie, pas la cohérence FX.
- Les balances sont écrites par `anvil_setStorageAt` (slots : USDC 9, USD₮/USAT 51, wFIAT ERC-7201 OZ). Si un token change de layout, `setTokenBalance` échoue explicitement.
- Le test négatif « DB » met à jour toutes les lignes `invoices` (pas de `drizzle-orm` dans les dépendances du worker, `eq` indisponible sans modifier package.json/lockfile). Les factures précédentes sont déjà finales, donc sans effet.
- Confirmations de l'indexer à 0 (anvil auto-mine) : le chemin avec 5 confirmations n'est pas couvert ici.
- Le fichier harness importe `apps/web/lib/**` par chemin relatif (pas de package) et dérive les types grammY depuis `buildBot` (grammy n'est pas une dépendance du worker).
